# Stage 4 — the ATL server (dual interface, type library, events)

**Used by:** Labs 5.1, 5.2, 6.2, 6.3

This is the one stage with **no source files in the repo**, and that is deliberate: an ATL project
is generated by the Visual Studio wizard, and reproducing its dozen files by hand would teach you
nothing and rot with every VS release. What follows is the exact wizard recipe. Allow **15–20
minutes** — the wizard pages are quick, but adding the members one dialog at a time, editing the
IDL and getting the build order right is where the time goes. It is also the "after" side of Lab 6.1's comparison.

## Prerequisite

Visual Studio with the optional component **C++ ATL for latest build tools (x86 & x64)**. If you
have no *ATL Project* template, that component is missing — add it in the Visual Studio Installer.

## Steps

### 1. Create the project

**File → New → Project → ATL Project**

| Setting | Value |
|---|---|
| Name | `TrainingCalc` |
| Application type | **Dynamic-link library (DLL)** |
| Support MFC | off |
| Support COM+ 1.0 | off |

> **The wizard creates two projects, not one.** `TrainingCalc` is your component. `TrainingCalcPS`
> is the proxy/stub project (Module 4) — the wizard writes it for you from the generated IDL.
> **Everything in this recipe is done in `TrainingCalc`.** You will not touch `TrainingCalcPS`;
> it only needs building and registering if you later take the object across an apartment or
> process boundary, and this stage's dual interface uses typelib marshaling anyway.

### 2. Add the object

Right-click the **`TrainingCalc`** project → **Add → New Item → ATL → ATL Simple Object**

| Wizard page | Setting | Value |
|---|---|---|
| Names | Short name | `Calculator` |
| Names | **ProgID** | **`TrainingCalc.Calculator`** — see below |
| Options | Threading model | **Both** |
| Options | Interface | **Dual** |
| Options | Aggregation | No |
| Options | Support `ISupportErrorInfo` | **checked** |
| Options | Support Connection Points | **checked** |

> **Do not leave the ProgID box empty.** Recent Visual Studio versions leave it blank, and a blank
> ProgID means the generated `Calculator.rgs` registers **only the CLSID**. Everything still builds,
> `regsvr32` still reports success — and then `New-Object -ComObject TrainingCalc.Calculator.1` fails,
> because there is no name for COM to look up. Type the ProgID in now and the whole lab works;
> §6 shows how to repair a project where it was missed.

"Dual" is what gives you a vtable *and* `IDispatch`, so C++, PowerShell, VBScript, and C# can all
call it — that is Lab 5.1.

**Support Connection Points** does all the event wiring for you in this one pass, and you will not
run a wizard again: it adds the `IConnectionPointContainerImpl` base class, the
`COM_INTERFACE_ENTRY(IConnectionPointContainer)`, the connection point map, an empty
`_ICalculatorEvents` dispinterface in the IDL, and a `_ICalculatorEvents_CP.h` holding an empty
proxy class. Step 4 fills in the two blanks it left.

### 3. Add the methods

**Class View** is a separate window from Solution Explorer, and it is usually not open by default:
**View → Class View** (`Ctrl+Shift+C`). It docks beside Solution Explorer and lists *types* rather
than files.

Expand `TrainingCalc` and you will find `ICalculator` — the interface, not the `CCalculator` class.
Add the methods there, so the wizard updates the `.idl`, the class declaration and the stub
implementation together:

Right-click `ICalculator` → **Add → Add Method** for each. **The return type is `HRESULT` every time** — the wizard fixes it and will not let you change it, because that is COM's calling convention (Module 1). The value the caller actually wants comes back through the `[out, retval]` parameter instead:

| Method | Returns | Parameters |
|---|---|---|
| `Add` | `HRESULT` | `[in] LONG a`, `[in] LONG b`, `[out, retval] LONG* result` |
| `Subtract` | `HRESULT` | `[in] LONG a`, `[in] LONG b`, `[out, retval] LONG* result` |
| `Divide` | `HRESULT` | `[in] LONG a`, `[in] LONG b`, `[out, retval] LONG* result` |
| `SumTo` | `HRESULT` | `[in] LONG n`, `[out, retval] LONG* total` |
| `Describe` | `HRESULT` | `[out, retval] BSTR* description` |

`Divide` is the one that can fail, which is what makes it useful: Lab 5.1 calls `Divide(10, 0)` from
PowerShell and VBScript to watch a rich error cross into a scripting language.

That is why PowerShell can write `$calc.Add(2, 3)` and get `5`: `[retval]` tells every Automation
caller "this parameter is the return value", and the `HRESULT` becomes an exception if it fails.

In the Add Method dialog, type each parameter's name and type, tick the direction attributes
(`in`, `out`, `retval`), and click **Add** before moving to the next one — a parameter you forget to
add stays missing even though it is still in the edit boxes.

Then right-click `ICalculator` → **Add → Add Property**: `LONG Precision`, with both get and put.

> **Editing the `.idl` by hand works too**, and after a few methods it is faster. But do it *only*
> if you also add the matching declaration to `CCalculator` and an implementation in the `.cpp`;
> the wizard's value is that it keeps those three in step.

**Checkpoint.** Open `TrainingCalc.idl` — the interface should now read:

```idl
interface ICalculator : IDispatch
{
    [id(1)] HRESULT Add([in] LONG a, [in] LONG b, [out, retval] LONG* result);
    [id(2)] HRESULT Subtract([in] LONG a, [in] LONG b, [out, retval] LONG* result);
    [id(3)] HRESULT Divide([in] LONG a, [in] LONG b, [out, retval] LONG* result);
    [id(4)] HRESULT SumTo([in] LONG n, [out, retval] LONG* total);
    [id(5)] HRESULT Describe([out, retval] BSTR* description);
    [propget, id(6)] HRESULT Precision([out, retval] LONG* pVal);
    [propput, id(6)] HRESULT Precision([in] LONG newVal);
};
```

Two things to notice, both of which the module discusses:

- **The wizard numbered the DISPIDs for you**, in the order you added the members, and gave the
  property's get and put the *same* id — that pairing is what makes it one property rather than two
  methods (§5.3). If your numbers differ because you added things in another order, that is fine;
  what matters is that they never change again once a client has been compiled against them
  (Module 4's versioning rule).
- **`Describe` is an ordinary member here.** Module 5 §5.3 shows it as `[id(DISPID_VALUE)]`, the
  **default member**, so that `$calc` on its own returns the description. The wizard will not do
  that for you; if you want that behaviour, change its id to `DISPID_VALUE` by hand.

### 4. Add the events (needed for Lab 5.2)

Step 2 created the event dispinterface and its proxy class, both empty. Two things go in them: the
event *declarations*, and the `Fire_*` helpers that call them. There is no wizard for the second
part that can be trusted to run twice, so you will paste it — which is worth doing anyway, because
that code is exactly what §5.7 describes.

**4a. Declare the two events.** In Class View, expand **`TrainingCalc` → `TrainingCalcLib`** — the
type library node — where `_ICalculatorEvents` sits beside the `Calculator` coclass, rather than at
the top level with `ICalculator`:

```
TrainingCalc
├── CCalculator
├── CProxy_ICalculatorEvents<T>
├── ICalculator                 <- the incoming interface, from step 3
└── TrainingCalcLib             <- the type library
    ├── Calculator              <- the coclass
    ├── _ICalculatorEvents      <- the outgoing interface: add the events HERE
    └── stdole2.tlb
```

That placement is not an accident. `ICalculator` is an interface the object *implements*, so it sits
with the class; `_ICalculatorEvents` is an **outgoing** interface the object only *calls*, and it
exists as a type library entry so clients and tools can discover it (§5.7).

Right-click `_ICalculatorEvents` → **Add → Add Method**:

| Method | Returns | Parameters |
|---|---|---|
| `OnProgress` | `void` | `[in] LONG percent` |
| `OnError` | `void` | `[in] BSTR message` |

**Here the return type is `void`, not `HRESULT`** — the one place in this recipe where it differs.
Event methods conventionally return nothing, because the source is broadcasting to several sinks and
has no sensible way to act on one of them failing.

Check `TrainingCalc.idl` afterwards; the dispinterface should read:

```idl
dispinterface _ICalculatorEvents
{
    properties:
    methods:
        [id(1)] void OnProgress([in] LONG percent);
        [id(2)] void OnError([in] BSTR message);
};
```

**4b. Write the `Fire_*` helpers.** Open `_ICalculatorEvents_CP.h`. Step 4a did not touch it — the
class is still empty:

```cpp
template<class T>
class CProxy_ICalculatorEvents :
    public ATL::IConnectionPointImpl<T, &__uuidof(_ICalculatorEvents)>
{
public:
                          // <- the two helpers go here
};
```

> **Why doesn't 4a fill this in?** Because two unrelated generators are involved. **Add Method**
> edits the `.idl` and nothing else. The `CProxy_` class was produced **once**, by the Support
> Connection Points checkbox in step 2, from whatever the type library held at that moment — which
> was an event set with no methods. Nothing watches the IDL afterwards and refreshes it. Visual
> Studio's only way to regenerate the class is the Add Connection Point wizard, and that is the one
> that appends a duplicate connection point map. Pasting is the shorter path, and you get to read
> the code you are relying on.

Replace the whole file with this. The two methods are what ATL's generator would have produced, and
they are the loop §5.7 talks about: walk the connection point's sink list, `QueryInterface` each sink
for `IDispatch`, and `Invoke` it with the event's DISPID.

```cpp
#pragma once

template<class T>
class CProxy_ICalculatorEvents :
    public ATL::IConnectionPointImpl<T, &__uuidof(_ICalculatorEvents)>
{
public:
    HRESULT Fire_OnProgress(LONG percent)
    {
        T* pT = static_cast<T*>(this);
        int cConnections = this->m_vec.GetSize();

        for (int i = 0; i < cConnections; ++i)
        {
            pT->Lock();
            CComPtr<IUnknown> punkConnection = this->m_vec.GetAt(i);
            pT->Unlock();

            CComQIPtr<IDispatch> pDispatch(punkConnection);
            if (!pDispatch) continue;

            CComVariant avarParams[1];
            avarParams[0] = percent;
            avarParams[0].vt = VT_I4;
            DISPPARAMS params = { avarParams, NULL, 1, 0 };
            pDispatch->Invoke(1, IID_NULL, LOCALE_USER_DEFAULT,    // 1 = [id(1)] OnProgress
                              DISPATCH_METHOD, &params, NULL, NULL, NULL);
        }
        return S_OK;
    }

    HRESULT Fire_OnError(BSTR message)
    {
        T* pT = static_cast<T*>(this);
        int cConnections = this->m_vec.GetSize();

        for (int i = 0; i < cConnections; ++i)
        {
            pT->Lock();
            CComPtr<IUnknown> punkConnection = this->m_vec.GetAt(i);
            pT->Unlock();

            CComQIPtr<IDispatch> pDispatch(punkConnection);
            if (!pDispatch) continue;

            CComVariant avarParams[1];
            avarParams[0] = message;
            avarParams[0].vt = VT_BSTR;
            DISPPARAMS params = { avarParams, NULL, 1, 0 };
            pDispatch->Invoke(2, IID_NULL, LOCALE_USER_DEFAULT,    // 2 = [id(2)] OnError
                              DISPATCH_METHOD, &params, NULL, NULL, NULL);
        }
        return S_OK;
    }
};
```

The `1` and `2` passed to `Invoke` are the DISPIDs from your IDL. If yours differ, match them.

> **Do not run Add → Add Connection Point.** Step 2 already added the base class and both maps.
> Running the wizard now appends a *second* connection point map and the build fails with
> `error C2535: 'GetConnMap': member function already defined`.

**4c. Build** (`Ctrl+Shift+B`). It should compile cleanly, and typing `Fire_` inside a `CCalculator`
method should now offer both helpers.

### 5. Implement and fire

All of this goes in **`Calculator.cpp`** — the implementation file the ATL Simple Object wizard
created alongside `Calculator.h`.

Step 3 already put empty stubs there, one per method you added, each returning `S_OK` with a
`// TODO: Add your implementation code here` comment. Replace the bodies; leave the signatures
alone, because they must keep matching the declarations in `Calculator.h` and the `.idl`.

```cpp
STDMETHODIMP CCalculator::Add(LONG a, LONG b, LONG* result)
{
    if (!result) return E_POINTER;
    *result = a + b;
    return S_OK;
}

// Slow on purpose: reports progress while it works (Module 5 §5.7).
STDMETHODIMP CCalculator::SumTo(LONG n, LONG* total)
{
    if (!total) return E_POINTER;
    *total = 0;
    LONG sum = 0;
    for (LONG i = 1; i <= n; ++i)
    {
        sum += i;
        if (n >= 100 && i % (n / 10) == 0)
            Fire_OnProgress(i / (n / 100));   // notifies every subscribed sink
    }
    *total = sum;
    return S_OK;
}

STDMETHODIMP CCalculator::Describe(BSTR* description)
{
    if (!description) return E_POINTER;
    *description = SysAllocString(L"Training Calculator 1.0");
    return *description ? S_OK : E_OUTOFMEMORY;
}
```

**The property needs somewhere to keep its value.** The wizard's `get_`/`put_` stubs both just
return `S_OK`, so as written the property forgets whatever you assign — and Lab 5.1 sets
`$calc.Precision = 4` and reads it back to prove the round trip. Add a member to `CCalculator` in
`Calculator.h`:

```cpp
private:
    LONG m_precision = 2;
```

and implement the pair in `Calculator.cpp`:

```cpp
STDMETHODIMP CCalculator::get_Precision(LONG* pVal)
{
    if (!pVal) return E_POINTER;
    *pVal = m_precision;
    return S_OK;
}

STDMETHODIMP CCalculator::put_Precision(LONG newVal)
{
    m_precision = newVal;
    return S_OK;
}
```

Two `HRESULT` methods sharing one DISPID are what a caller sees as a single read/write property
(§5.3) — which is why `$calc.Precision = 4` and `$calc.Precision` reach different functions here.

For Lab 5.1's error handling, return rich errors rather than a bare `HRESULT`:

```cpp
STDMETHODIMP CCalculator::Divide(LONG a, LONG b, LONG* result)
{
    if (!result) return E_POINTER;
    *result = 0;
    if (b == 0) return Error(L"Cannot divide by zero.", IID_ICalculator, E_INVALIDARG);
    *result = a / b;
    return S_OK;
}
```

### 6. Build and register

Build **x64 / Debug**. Registration is the step people lose time on, so verify it rather than
assuming it.

**6a. Register the DLL.** An ATL DLL project has **Register Output** on by default, so the build
runs `regsvr32` on the result — but only if Visual Studio has the rights to write the keys. Pick one
of these:

| | How | Writes to |
|---|---|---|
| **Per-user (recommended)** | Project **Properties → Configuration Properties → General → Per-user Redirection = Yes**, then rebuild | `HKCU\Software\Classes` — no admin needed |
| **Machine-wide** | Run Visual Studio **as administrator**, then rebuild | `HKLM\Software\Classes` |
| **By hand** | Set **Register Output = No**, then `regsvr32 "<path>\x64\Debug\TrainingCalc.dll"` from an elevated prompt | `HKLM\Software\Classes` |

Per-user redirection is the better habit: no elevation, and clients running as you still find the
component, because `HKCR` is the merged view of both hives (Module 2 §2.2).

**6b. Confirm it actually registered.** The build output is not proof — look in the registry:

```powershell
Get-ItemProperty "Registry::HKEY_CLASSES_ROOT\TrainingCalc.Calculator.1\CLSID"
```

That should print a CLSID.

> **If that path does not exist**, the class is almost certainly registered but has **no ProgID** —
> the blank-ProgID trap from step 2. Confirm by finding the class through its DLL instead:
>
> ```powershell
> Get-ChildItem "Registry::HKEY_CLASSES_ROOT\CLSID" |
>   Where-Object { (Get-ItemProperty "$($_.PSPath)\InprocServer32" -EA SilentlyContinue).'(default)' -like '*TrainingCalc.dll' } |
>   Select-Object -ExpandProperty PSChildName
> ```
>
> If that prints a CLSID, the component registered fine and only the name is missing. Fix it by
> adding the ProgID to **`Calculator.rgs`** — open it and make it look like this, substituting your
> own CLSID:
>
> ```
> HKCR
> {
>     TrainingCalc.Calculator.1 = s 'Calculator Class'
>     {
>         CLSID = s '{YOUR-CLSID-HERE}'
>     }
>     TrainingCalc.Calculator = s 'Calculator Class'
>     {
>         CLSID = s '{YOUR-CLSID-HERE}'
>         CurVer = s 'TrainingCalc.Calculator.1'
>     }
>     NoRemove CLSID
>     {
>         ForceRemove {YOUR-CLSID-HERE} = s 'Calculator Class'
>         {
>             ProgID = s 'TrainingCalc.Calculator.1'
>             VersionIndependentProgID = s 'TrainingCalc.Calculator'
>             ForceRemove 'Programmable'
>             InprocServer32 = s '%MODULE%'
>             {
>                 val ThreadingModel = s 'Both'
>             }
>             'TypeLib' = s '{YOUR-LIBID-HERE}'
>         }
>     }
> }
> ```
>
> Then unregister, rebuild, and register again — `regsvr32 /u` first, or the old keys linger.
> This is the same ProgID → CLSID → `InprocServer32` chain you walked by hand in Module 2 §2.2; here
> you are writing it rather than reading it.

**6c. Create one.**

```powershell
$calc = New-Object -ComObject TrainingCalc.Calculator.1
$calc.Add(2, 3)          # 5
```

> **`New-Object` reporting `CLSID {00000000-0000-0000-0000-000000000000}`** means the **ProgID
> string was not found at all** — PowerShell shows a zero CLSID when it cannot resolve the name.
> Check the spelling against 6b's output. The wizard builds the ProgID from the **project** name, so
> a project called `TrainingCalc` gives `TrainingCalc.Calculator.1`.
>
> Note this is a *different* component from the hand-written `Training.Calculator.1` of Modules 2–4.
> Both can be registered at once; they have different CLSIDs and different ProgIDs.

ATL's `DllRegisterServer` registers the CLSID, the ProgID, **and** the type library — all three,
which is why Lab 5.1's scripting clients work without any extra step.

## Verify

```powershell
$calc = New-Object -ComObject TrainingCalc.Calculator.1
$calc.Add(40, 2)                       # -> 42
$calc.Describe()                       # -> Training Calculator 1.0
[Runtime.InteropServices.Marshal]::ReleaseComObject($calc) | Out-Null
```

If `New-Object -ComObject` finds it by ProgID and `Add` returns a number rather than an HRESULT,
the dual interface and the type library are both working correctly.

> Your ProgID depends on the project name — the wizard builds it as
> `<ProjectName>.<ObjectName>.1`. Check `HKCR\TrainingCalc.Calculator.1` if in doubt.
